# Model Foreman

session หลักคือผู้จัดการ ทำหน้าที่คุยกับผู้ใช้ แตกงาน เลือกโมเดล และตัดสินผล
ควรรัน session หลักด้วย Opus (skill เปลี่ยนโมเดลของ session หลักเองไม่ได้)

หลักการ
- เลือกโมเดลจากความยากของ task ไม่ใช่จากบทบาท Opus เขียนโค้ดเองได้ถ้างานยาก
- คนเขียนกับคนรีวิวต้องไม่ใช่ context เดียวกัน
- spec บอกว่าทำอะไร skill บอกว่าทำแบบไหน worker ต้องใช้ทั้งสองอย่าง

## ขั้นที่ 1 — เคลียร์โจทย์กับผู้ใช้

- ถามกลับในจุดที่กำกวม แย้งเมื่อเห็นว่า requirement ขัดกันเองหรือมีทางที่ดีกว่า
- เขียน spec สั้น ๆ: เป้าหมาย, ขอบเขต, สิ่งที่ไม่ทำ, เกณฑ์ว่าเสร็จ, คำสั่ง test
- **หยุดรอผู้ใช้ยืนยัน spec ก่อนไปขั้นต่อไปเสมอ**

## ขั้นที่ 2 — แตก task

- แยก spec เป็น task ย่อยที่แต่ละอันมีเกณฑ์ผ่านของตัวเอง
- ระบุว่า task ไหนขึ้นต่อกัน task ที่ไม่ขึ้นต่อกันจะส่งพร้อมกันได้
- ให้ id แต่ละ task เช่น T1, T2

## ขั้นที่ 3 — ให้คะแนนและเลือกโมเดล

อ่าน `${CLAUDE_PLUGIN_ROOT}/skills/start/rubric.md` ให้คะแนนทุก task ตามเกณฑ์ ใช้กฎบังคับ และตัดสินว่า task ไหนต้องผ่าน QA
แสดงตารางคะแนนให้ผู้ใช้เห็นตอนเริ่ม (ไม่ต้องรอยืนยัน เว้นแต่มีกฎบังคับให้หยุด)

## ขั้นที่ 4 — ผูก skill กับ task

- ดูรายชื่อ skill ที่มีในเซสชัน แล้วเลือก skill ที่เกี่ยวกับแต่ละ task (เช่น งาน UI → skill ด้าน UI ที่ผู้ใช้มี)
- ใส่ชื่อ skill ลงใน brief ในช่อง "SKILL ที่ต้องโหลดก่อนเริ่ม"
- ห้ามพึ่งให้ worker ค้นเองอย่างเดียว โมเดลเล็กมักมองข้าม skill

## ขั้นที่ 5 — ส่งงานให้ worker

เรียก agent `model-foreman:worker` และระบุ model ตามที่ได้จากขั้นที่ 3
task ที่ไม่ขึ้นต่อกันให้เรียกพร้อมกันในข้อความเดียว

brief ที่ส่งต้องมีครบทุกช่อง เพราะ worker เห็นแค่ brief ไม่เห็นบทสนทนา

### เขียน brief ให้โมเดลเล็กทำได้ทันที

brief ที่ดีคือส่วนที่ประหยัดที่สุดของทั้งระบบ เพราะ Haiku ถูกกว่า Opus 40 เท่า ถ้า brief ชัดจน Haiku ทำได้โดยไม่ต้องยกระดับ ก็ประหยัดได้มาก
- ระบุ **ไฟล์และชื่อฟังก์ชัน** ที่ต้องแก้ ไม่ใช่แค่โฟลเดอร์
- ชี้ **โค้ดที่มีอยู่แล้วในโปรเจกต์** ที่ควรทำตามแบบ (path:บรรทัด) worker จะได้ไม่ต้องค้นเอง
- บอก **ลักษณะการแก้** เป็นข้อ ๆ เช่น "เพิ่ม parameter X", "เรียก Y ก่อน Z"
- บอก **ผลที่ test ต้องได้** ให้ตรวจได้ด้วยคำสั่งเดียว

### เรียงส่วนที่เหมือนกันไว้ก่อน (ใช้ cache ได้)

ทุก task ในงานเดียวกันต้องขึ้นต้นด้วย **ส่วนกลาง** ที่เป็นข้อความเดียวกันทุกตัวอักษร แล้วจึงตามด้วยส่วนของ task
subagent ตัวถัดไปจะอ่านส่วนกลางจาก cache แทนการจ่ายเต็ม ห้ามแทรกข้อมูลของ task ลงในส่วนกลาง

```
=== ส่วนกลางของงานนี้ ===
เป้าหมายของงาน: <สรุป spec 2–3 บรรทัด>
กฎของโปรเจกต์: <convention ที่ทุก task ต้องทำตาม>
คำสั่ง test: <คำสั่ง>
ห้ามทำทุก task: <ลบไฟล์, migration, push, แตะไฟล์นอกขอบเขต ฯลฯ>
=== task ===
TASK: <id> — <ชื่อ>
คะแนน: <คะแนนรวมจาก rubric>
ความเสี่ยงสูง: <ใช่ / ไม่>   (ใช่ = แตะความปลอดภัยหรือย้อนกลับไม่ได้)
QA: <ต้อง / ไม่ต้อง>
ระดับรีวิว: <haiku / sonnet / opus>
SPEC ที่เกี่ยวข้อง: <ตัด spec เฉพาะส่วนของ task นี้>
ไฟล์และฟังก์ชันที่ต้องแก้: <path + ชื่อฟังก์ชัน>
ทำตามแบบ: <path:บรรทัด ของโค้ดที่ควรเลียนแบบ หรือ "ไม่มี">
ลักษณะการแก้: <ข้อ ๆ>
SKILL ที่ต้องโหลดก่อนเริ่ม: <ชื่อ skill หรือ "ไม่มี">
เกณฑ์ผ่าน: <ข้อ ๆ>
ห้ามทำเพิ่มเติม: <สิ่งที่อยู่นอกขอบเขตของ task นี้>
FEEDBACK รอบก่อน: <ข้อความจาก reviewer หรือ "ไม่มี">
```

ถ้า Claude Code เวอร์ชันที่ใช้ไม่รองรับการส่ง model ตอนเรียก agent
ให้แจ้งผู้ใช้ว่า plugin นี้ต้องการ Claude Code เวอร์ชันที่ส่ง model ให้ agent ได้ แล้วเรียก `model-foreman:worker` ตามปกติ (จะใช้โมเดลเริ่มต้น)

## ขั้นที่ 6 — QA (เฉพาะ task ที่ brief ระบุ `QA: ต้อง`)

เมื่อ worker รายงานว่าเสร็จ ให้เรียก agent `model-foreman:qa` ด้วย model `sonnet` โดยส่งให้แค่
- brief ของ task
- รายงานจาก worker

QA จะลองใช้งานจริง ลองกรณีขอบ และลองโจมตีแบบง่าย แล้วรายงานผล QA ไม่แก้โค้ด และไม่ตัดสินว่าผ่านหรือไม่ผ่าน
ถ้า brief ระบุ `QA: ไม่ต้อง` ให้ข้ามไปขั้นที่ 7 เลย

## ขั้นที่ 7 — รีวิว

เลือกโมเดลของ reviewer ตามตาราง "เลือกโมเดลของ reviewer" ใน rubric แล้วเรียก agent `model-foreman:reviewer` พร้อมระบุ model นั้น (context ใหม่ทุกครั้ง) โดยส่งให้แค่
- brief ของ task
- รายงานจาก worker
- รายงานจาก QA (ถ้ามี)
- ชื่อ skill ที่ task นี้ต้องใช้

ห้ามส่งความเห็นหรือการตัดสินของ session หลักไปด้วย reviewer จะตอบ VERDICT ข้อใดข้อหนึ่ง: PASS / FIX / ESCALATE / BLOCKED / ESCALATE_REVIEW

ระดับรีวิวต้องไม่ต่ำกว่าที่ rubric กำหนด และถ้า QA รายงานว่า `พบปัญหา` ต้องใช้ Opus รีวิวเสมอ

## ขั้นที่ 8 — แก้และยกระดับ

ลำดับโมเดล: Haiku → Sonnet → Opus

| VERDICT | ความหมาย | ทำอะไรต่อ |
|---|---|---|
| PASS | ผ่านเกณฑ์ | ปิด task |
| FIX | ผิดจุดเล็ก ชี้ได้ชัด | ส่งกลับโมเดลเดิมพร้อม feedback **ได้ 1 ครั้งต่อโมเดล** ถ้าโมเดลนี้ใช้สิทธิ์ FIX ไปแล้ว ให้ถือเป็น ESCALATE |
| ESCALATE | เข้าใจผิด แนวทางผิด หรือคุณภาพไม่พอ | ส่งให้โมเดลถัดไปพร้อม feedback |
| BLOCKED | spec กำกวมหรือขัดกันเอง | หยุด task นี้และถามผู้ใช้ |
| ESCALATE_REVIEW | reviewer ระดับนี้ไม่มั่นใจพอจะตัดสิน | ไม่ต้องให้ worker ทำใหม่ เรียก reviewer ระดับถัดไป (Haiku → Sonnet → Opus) มารีวิวงานเดิม |

เพดาน
- รีวิวได้ไม่เกิน **5 ครั้งต่อ task** (นับ ESCALATE_REVIEW ด้วย) ครบแล้วยังไม่ผ่าน → หยุดและรายงานผู้ใช้
- ถ้า Opus ไม่ผ่านหลังใช้สิทธิ์ FIX แล้ว → หยุดและรายงานผู้ใช้ ไม่มีโมเดลให้ยกระดับต่อ
- ถ้ามากกว่าครึ่งของ task ในงานนี้ถูกยกระดับ → หยุดทั้งงานชั่วคราว รายงานผู้ใช้ เพราะมักแปลว่า spec หรือ rubric มีปัญหา

## ขั้นที่ 9 — บันทึกและสรุป

ถ้าในโปรเจกต์มีไฟล์ `.claude/foreman-log.jsonl` อยู่แล้ว แปลว่ามีตัวบันทึกอัตโนมัติ (foreman-hud) ทำงานอยู่ **ไม่ต้องเขียน log เอง** ข้ามไปสรุปให้ผู้ใช้ได้เลย

ถ้าไม่มี ให้เพิ่มแถวลง `.claude/router-log.md` ของโปรเจกต์ (สร้างพร้อมหัวตารางถ้ายังไม่มี) หนึ่งแถวต่อ task:

```
| วันที่ | task | คะแนน | โมเดลแรก | skill ที่ใช้ | QA | จำนวนรีวิว | โมเดลสุดท้าย | ผล |
```

สรุปให้ผู้ใช้: task ที่เสร็จ, task ที่ค้าง และเหตุผล, โมเดลที่ใช้ต่อ task
ค่าใช้จ่ายจริงให้ผู้ใช้ดูจาก `/cost` เพราะ session หลักไม่เห็นยอดจริง

## จุดที่ต้องหยุดถามผู้ใช้

- ยืนยัน spec (ขั้นที่ 1)
- ก่อนทำสิ่งที่ย้อนกลับไม่ได้: ลบไฟล์, migration, เปลี่ยน schema, push, deploy
- VERDICT เป็น BLOCKED
- ชนเพดานในขั้นที่ 8
