# Model Foreman

session หลักคือผู้จัดการ ทำหน้าที่คุยกับผู้ใช้ แตกงาน เลือกโมเดล และตัดสินผล
ควรรัน session หลักด้วย Opus และ effort `high` หรือ `xhigh` (skill เปลี่ยนโมเดลหรือ effort ของ session หลักเองไม่ได้)
effort ของ session หลักไม่มีผลกับ agent เพราะทุกครั้งที่เรียก agent ต้องส่ง effort เองตาม rubric

หลักการ
- เลือกโมเดลจากความยากของ task ไม่ใช่จากบทบาท Opus เขียนโค้ดเองได้ถ้างานยาก
- คนเขียนกับคนรีวิวต้องไม่ใช่ context เดียวกัน
- spec บอกว่าทำอะไร skill บอกว่าทำแบบไหน worker ต้องใช้ทั้งสองอย่าง

## ขั้นที่ 1 — เคลียร์โจทย์กับผู้ใช้

- ถามกลับในจุดที่กำกวม แย้งเมื่อเห็นว่า requirement ขัดกันเองหรือมีทางที่ดีกว่า
- เขียน spec สั้น ๆ: เป้าหมาย, ขอบเขต, สิ่งที่ไม่ทำ, เกณฑ์ว่าเสร็จ, คำสั่ง test
- **หยุดรอผู้ใช้ยืนยัน spec ก่อนไปขั้นต่อไปเสมอ**

## ขั้นที่ 2 — แตก task

- แยก spec เป็น task ย่อยที่แต่ละอันมีเกณฑ์ผ่านของตัวเอง
- ระบุว่า task ไหนขึ้นต่อกัน task ที่ไม่ขึ้นต่อกันจะส่งพร้อมกันได้
- ระบุไฟล์ที่แต่ละ task จะแก้หรือสร้าง **task ที่ไฟล์ซ้อนกันให้นับว่าขึ้นต่อกัน** และทำทีละตัว แม้เนื้องานจะไม่เกี่ยวกัน เพราะ worker สองตัวแก้ไฟล์เดียวกันพร้อมกันจะทับงานกัน
- ตั้ง run id ให้งานนี้หนึ่งค่า เช่น `R-20261109-otapproval` (วันที่ + ชื่อสั้นของงาน) ใช้ค่าเดิมตลอดงาน แม้จะเปิด session ใหม่มาทำต่อ
- ให้ id แต่ละ task เช่น T1, T2 (ซ้ำกับงานก่อน ๆ ได้ เพราะแยกด้วย run id) ห้ามใช้ `FINAL` ซึ่งสงวนไว้สำหรับรีวิวรวม
- บันทึกแผนลง `.claude/foreman/plan-<run>.md`: spec ที่ผู้ใช้ยืนยัน และตาราง `| id | ชื่อ | ไฟล์ | ขึ้นกับ | คะแนน | โมเดล | สถานะ |` อัปเดตช่องสถานะทุกครั้งที่ task ปิด
- ถ้าผู้ใช้สั่งให้ทำ run เดิมต่อ ให้อ่านไฟล์แผนนี้ก่อน แล้วทำต่อจาก task ที่ยังไม่ปิด

## ขั้นที่ 3 — ให้คะแนนและเลือกโมเดล

อ่าน `${CLAUDE_PLUGIN_ROOT}/skills/start/rubric.md` ให้คะแนนทุก task ตามเกณฑ์ ใช้กฎบังคับ และตัดสินว่า task ไหนต้องผ่าน QA
แสดงตารางคะแนนให้ผู้ใช้เห็นตอนเริ่ม (ไม่ต้องรอยืนยัน เว้นแต่มีกฎบังคับให้หยุด)

## ขั้นที่ 4 — ผูก skill กับ task

- ดูรายชื่อ skill ที่มีในเซสชัน แล้วเลือกตามประเภทงาน ใช้เฉพาะ skill ที่มีอยู่จริงในเซสชัน

| ประเภท task | skill ที่ควรผูก (ถ้ามี) |
|---|---|
| หน้าจอ, component, dashboard ในแอปที่มีอยู่ | `interface-design`, `dashboard-design` |
| flow การใช้งาน, ฟอร์มหลายขั้น | `ux-audit` |
| ทุกงาน UI (ให้ reviewer ใช้ตรวจ) | `web-design-guidelines` |
| QA ของงาน UI | `visual-check` (playwright-eyes) |
| backend / frontend ทั่วไป | skill ด้าน backend / frontend ที่ผู้ใช้มี |

- ใส่ "ไม่มี" ได้เฉพาะเมื่อไม่มี skill ไหนเกี่ยวจริง ๆ ไม่ใช่เพราะไม่ได้ดู
- ใส่ชื่อ skill ลงใน brief ในช่อง "SKILL ที่ต้องโหลดก่อนเริ่ม"
- ห้ามพึ่งให้ worker ค้นเองอย่างเดียว โมเดลเล็กมักมองข้าม skill

## ขั้นที่ 5 — ส่งงานให้ worker

เรียก agent `model-foreman:worker` โดยระบุ model ตามที่ได้จากขั้นที่ 3 และ effort ตามตาราง "เลือก effort" ใน rubric
task ที่ไม่ขึ้นต่อกันให้เรียกพร้อมกันในข้อความเดียว ช่อง `ไฟล์` ของ task ที่ส่งพร้อมกันต้องไม่ซ้อนกัน (foreman-hud จะปฏิเสธ worker ที่ไฟล์ซ้อนกับ worker ที่ยังทำอยู่)

brief ที่ส่งต้องมีครบทุกช่อง เพราะ worker เห็นแค่ brief ไม่เห็นบทสนทนา

### เขียน brief ให้โมเดลเล็กทำได้ทันที

brief ที่ดีคือส่วนที่ประหยัดที่สุดของทั้งระบบ เพราะ Haiku ถูกกว่า Opus 40 เท่า ถ้า brief ชัดจน Haiku ทำได้โดยไม่ต้องยกระดับ ก็ประหยัดได้มาก
- ระบุ **ไฟล์และชื่อฟังก์ชัน** ที่ต้องแก้ ไม่ใช่แค่โฟลเดอร์
- ชี้ **โค้ดที่มีอยู่แล้วในโปรเจกต์** ที่ควรทำตามแบบ (path:บรรทัด) worker จะได้ไม่ต้องค้นเอง
- บอก **ลักษณะการแก้** เป็นข้อ ๆ เช่น "เพิ่ม parameter X", "เรียก Y ก่อน Z"
- บอก **ผลที่ test ต้องได้** ให้ตรวจได้ด้วยคำสั่งเดียว

### เรียงส่วนที่เหมือนกันไว้ก่อน (ใช้ cache ได้)

ทุก task ในงานเดียวกันต้องขึ้นต้นด้วย **ส่วนกลาง** ที่เป็นข้อความเดียวกันทุกตัวอักษร แล้วจึงตามด้วยส่วนของ task
subagent ตัวถัดไปจะอ่านส่วนกลางจาก cache แทนการจ่ายเต็ม ห้ามแทรกข้อมูลของ task ลงในส่วนกลาง

```
=== ส่วนกลางของงานนี้ ===
RUN: <run id>
เป้าหมายของงาน: <สรุป spec 2–3 บรรทัด>
กฎของโปรเจกต์: <convention ที่ทุก task ต้องทำตาม>
คำสั่ง test: <คำสั่ง>
ห้ามทำทุก task: <ลบไฟล์, migration, push, commit, แตะไฟล์นอกขอบเขต ฯลฯ>
สคริปต์ patch: bash ${CLAUDE_PLUGIN_ROOT}/scripts/foreman-patch.sh
QA เข้าระบบ: <URL, คำสั่งเปิด dev server, บัญชีทดสอบ — คัดจาก .claude/foreman/qa-env.md หรือ "ไม่มี">
=== task ===
TASK: <id> — <ชื่อ>
คะแนน: <คะแนนรวมจาก rubric>
ความเสี่ยงสูง: <ใช่ / ไม่>   (ใช่ = แตะความปลอดภัยหรือย้อนกลับไม่ได้)
QA: <ต้อง / ไม่ต้อง>
ระดับรีวิว: <haiku / sonnet / opus>
effort: <low / medium / high>   (ของ agent ที่รับ brief นี้)
TDD: <ต้อง / ไม่ต้อง>   (ต้อง เมื่อ "ตรวจได้ง่ายไหม" ได้ 2)
อ่านเพิ่มได้ไม่เกิน: <จำนวนไฟล์ตาม rubric หรือ "ไม่จำกัด">
SPEC ที่เกี่ยวข้อง: <ตัด spec เฉพาะส่วนของ task นี้>
ไฟล์: <path ทุกไฟล์ที่จะแก้หรือสร้าง คั่นด้วย , >
ฟังก์ชันที่ต้องแก้: <ชื่อฟังก์ชัน / component ในแต่ละไฟล์>
ทำตามแบบ: <path:บรรทัด ของโค้ดที่ควรเลียนแบบ หรือ "ไม่มี">
ลักษณะการแก้: <ข้อ ๆ>
SKILL ที่ต้องโหลดก่อนเริ่ม: <ชื่อ skill หรือ "ไม่มี">
เกณฑ์ผ่าน: <ข้อ ๆ>
ห้ามทำเพิ่มเติม: <สิ่งที่อยู่นอกขอบเขตของ task นี้>
FEEDBACK รอบก่อน: <ข้อความจาก reviewer หรือ "ไม่มี">
```

ถ้าโปรเจกต์มี `.claude/foreman/qa-env.md` ให้อ่านครั้งเดียวตอนเริ่มงาน แล้วคัดลงช่อง "QA เข้าระบบ" ถ้าไม่มีไฟล์และมี task ที่ต้อง QA งาน UI ให้ถามผู้ใช้ตอนยืนยัน spec ว่า QA จะเข้าระบบอย่างไร

**brief คือสัญญา** ส่งไปแล้วห้ามเพิ่ม requirement ให้ worker ตัวที่กำลังทำ ถ้าระหว่างทางเจอสิ่งที่ต้องทำเพิ่ม ให้สร้าง task ใหม่ (id ใหม่) หลัง task เดิมปิด

ถ้า Claude Code เวอร์ชันที่ใช้ไม่รองรับการส่ง model ตอนเรียก agent
ให้แจ้งผู้ใช้ว่า plugin นี้ต้องการ Claude Code เวอร์ชันที่ส่ง model ให้ agent ได้ แล้วเรียก `model-foreman:worker` ตามปกติ (จะใช้โมเดลเริ่มต้น)

### เมื่อ worker ตอบกลับ

| สถานะ | ทำอะไรต่อ |
|---|---|
| `DONE` | ไปขั้นที่ 6 (QA) หรือ 7 (รีวิว) |
| `DONE_WITH_CONCERNS` | อ่านข้อกังวลก่อน ถ้าเป็นเรื่องความถูกต้องหรือขอบเขต ให้ตัดสินใจก่อนรีวิว (แก้ brief แล้วส่งใหม่ หรือถามผู้ใช้) ถ้าเป็นแค่ข้อสังเกต ไปต่อได้ และส่งข้อกังวลให้ reviewer ด้วย |
| `NEEDS_CONTEXT` | ตอบคำถาม เติมลง brief แล้วส่งให้**โมเดลเดิม**อีกครั้ง ไม่นับเป็นการใช้สิทธิ์ FIX ถ้าตอบเองไม่ได้ ให้ถามผู้ใช้ |
| `BLOCKED` | ดูเหตุผล: ขาด context → เติมแล้วส่งโมเดลเดิม / ต้องคิดมากกว่านี้ → ยกระดับโมเดล / งานใหญ่ไป → แตกเป็น task ย่อย / spec ผิดหรือต้องทำสิ่งที่ย้อนกลับไม่ได้ → ถามผู้ใช้ ห้ามส่งให้โมเดลเดิมทำซ้ำโดยไม่เปลี่ยนอะไร |
| `DISPUTE` | ส่งให้ reviewer ระดับเดิมตัดสิน พร้อม feedback เดิมและข้อโต้แย้งของ worker ห้ามตัดสินเองแทน reviewer |

## ขั้นที่ 6 — QA (เฉพาะ task ที่ brief ระบุ `QA: ต้อง`)

เมื่อ worker รายงานว่าเสร็จ ให้เรียก agent `model-foreman:qa` ด้วย model `sonnet` และ effort ตาม rubric โดยส่งให้แค่
- brief ของ task
- รายงานจาก worker

QA จะลองใช้งานจริง ลองกรณีขอบ และลองโจมตีแบบง่าย แล้วรายงานผล QA ไม่แก้โค้ด และไม่ตัดสินว่าผ่านหรือไม่ผ่าน
ผล QA

| QA สถานะ / ระดับสูงสุด | ทำอะไรต่อ |
|---|---|
| `พบปัญหา` + `สูง` หรือ `กลาง` | **ยังไม่เรียก reviewer** ส่งปัญหาจาก QA กลับให้ worker โมเดลเดิมในช่อง FEEDBACK รอบก่อน (นับเป็นการใช้สิทธิ์ FIX ของโมเดลนั้น) แล้วให้ QA ลองซ้ำ จากนั้นจึงรีวิว |
| `พบปัญหา` + `ต่ำ` | ไปรีวิวได้เลย ส่งรายงาน QA ให้ reviewer ตัดสินว่าต้องแก้ไหม |
| `ไม่พบปัญหา` | ไปรีวิว |
| `ทดสอบไม่ได้` | แจ้งผู้ใช้ว่าติดอะไร (มักเป็น dev server หรือบัญชีทดสอบ) แล้วไปรีวิว โดยบอก reviewer ว่า QA ไม่ได้ทดสอบจริง |

ถ้า brief ระบุ `QA: ไม่ต้อง` ให้ข้ามไปขั้นที่ 7 เลย

## ขั้นที่ 7 — รีวิว

เลือกโมเดลของ reviewer ตามตาราง "เลือกโมเดลของ reviewer" ใน rubric แล้วเรียก agent `model-foreman:reviewer` พร้อมระบุ model และ effort ตาม rubric (context ใหม่ทุกครั้ง) โดยส่งให้แค่
- brief ของ task
- รายงานจาก worker
- รายงานจาก QA (ถ้ามี)
- ชื่อ skill ที่ task นี้ต้องใช้

ห้ามส่งความเห็นหรือการตัดสินของ session หลักไปด้วย reviewer จะตอบ VERDICT ข้อใดข้อหนึ่ง: PASS / FIX / ESCALATE / BLOCKED / ESCALATE_REVIEW

**ต้องส่ง model ทุกครั้ง** ใช้ค่าในช่อง `ระดับรีวิว` ของ brief ซึ่งเป็นทั้งขั้นต่ำและเพดาน ยกระดับได้เฉพาะเมื่อ
- reviewer รอบก่อนตอบ ESCALATE_REVIEW
- QA รายงาน `พบปัญหา` ระดับ `สูง` หรือ `กลาง` (ใช้ Opus)

ข้อสังเกตนอกขอบเขตจาก reviewer ไม่ใช่เหตุให้ทำ task เดิมต่อ ให้เก็บไว้เสนอผู้ใช้ตอนสรุปว่าจะสร้าง task ใหม่ไหม

## ขั้นที่ 8 — แก้และยกระดับ

ลำดับโมเดล: Haiku → Sonnet → Opus

| VERDICT | ความหมาย | ทำอะไรต่อ |
|---|---|---|
| PASS | ผ่านเกณฑ์ | ปิด task |
| FIX | ผิดจุดเล็ก ชี้ได้ชัด | ส่งกลับโมเดลเดิมพร้อม feedback **ได้ 1 ครั้งต่อโมเดล** (รวมรอบที่แก้ตาม QA) ถ้าโมเดลนี้ใช้สิทธิ์ FIX ไปแล้ว ให้ถือเป็น ESCALATE |
| ESCALATE | เข้าใจผิด แนวทางผิด หรือคุณภาพไม่พอ | ส่งให้โมเดลถัดไปพร้อม feedback |
| BLOCKED | spec กำกวมหรือขัดกันเอง | หยุด task นี้และถามผู้ใช้ |
| ESCALATE_REVIEW | reviewer ระดับนี้ไม่มั่นใจพอจะตัดสิน | ไม่ต้องให้ worker ทำใหม่ เรียก reviewer ระดับถัดไป (Haiku → Sonnet → Opus) มารีวิวงานเดิม |

เพดาน
- รีวิวได้ไม่เกิน **5 ครั้งต่อ task** (นับ ESCALATE_REVIEW ด้วย) ครบแล้วยังไม่ผ่าน → หยุดและรายงานผู้ใช้
- ถ้า Opus ไม่ผ่านหลังใช้สิทธิ์ FIX แล้ว → หยุดและรายงานผู้ใช้ ไม่มีโมเดลให้ยกระดับต่อ
- ถ้ามากกว่าครึ่งของ task ในงานนี้ถูกยกระดับ → หยุดทั้งงานชั่วคราว รายงานผู้ใช้ เพราะมักแปลว่า spec หรือ rubric มีปัญหา

## ขั้นที่ 9 — รีวิวรวมทั้งงาน

ทำเมื่อทุก task ในงานนี้ PASS แล้ว และมีมากกว่าหนึ่ง task (งานที่มี task เดียวข้ามไปขั้นที่ 10 ได้)

1. สร้าง patch ของทั้งงาน: `bash ${CLAUDE_PLUGIN_ROOT}/scripts/foreman-patch.sh all <run>`
2. เรียก `model-foreman:reviewer` ด้วย model `opus` effort `high` พร้อม brief นี้
   ```
   TASK: FINAL — รีวิวรวม <ชื่องาน>
   RUN: <run id>
   effort: high
   ระดับรีวิว: opus
   SPEC: <spec ที่ผู้ใช้ยืนยัน>
   TASK ทั้งหมด: <id, ชื่อ, เกณฑ์ผ่าน ของทุก task>
   patch ทั้งงาน: .claude/foreman/patches/<run>-ALL.patch
   คำสั่ง test ทั้งโปรเจกต์: <คำสั่ง>
   สคริปต์ patch: bash ${CLAUDE_PLUGIN_ROOT}/scripts/foreman-patch.sh
   ```

   BLOCKED → ถามผู้ใช้

## ขั้นที่ 10 — บันทึกและสรุป

ถ้าในโปรเจกต์มีไฟล์ `.claude/foreman-log.jsonl` อยู่แล้ว แปลว่ามีตัวบันทึกอัตโนมัติ (foreman-hud) ทำงานอยู่ **ไม่ต้องเขียน log เอง** ข้ามไปสรุปให้ผู้ใช้ได้เลย

ถ้าไม่มี ให้เพิ่มแถวลง `.claude/router-log.md` ของโปรเจกต์ (สร้างพร้อมหัวตารางถ้ายังไม่มี) หนึ่งแถวต่อ task:

```
| วันที่ | task | คะแนน | โมเดลแรก | skill ที่ใช้ | QA | จำนวนรีวิว | โมเดลสุดท้าย | ผล |
```

**ผู้จัดการและ agent ทุกตัวไม่ commit** งานทั้งหมดค้างเป็น uncommitted ใน working tree ให้ผู้ใช้ตรวจและ commit เอง

สรุปให้ผู้ใช้: task ที่เสร็จ, task ที่ค้าง และเหตุผล, โมเดลที่ใช้ต่อ task
- รายการไฟล์ที่เปลี่ยน (จาก patch ทั้งงาน) และ path ของ `<run>-ALL.patch`
- ร่างข้อความ commit ให้ผู้ใช้ copy ไปใช้ (บรรทัดแรกสั้น บอกว่าทำอะไร ตามด้วยรายการเปลี่ยนแปลง ไม่ใส่ชื่อ AI หรือ Co-Authored-By)
- ถ้าอยากย้อนทั้งงาน: `patch -R -p1 < .claude/foreman/patches/<run>-ALL.patch`
- หลัง commit แล้วลบ `.claude/foreman/snap/<run>/` ได้
และข้อสังเกตนอกขอบเขตที่ reviewer เก็บไว้ ถามผู้ใช้ว่าจะสร้างเป็น task ใหม่ไหม
ค่าใช้จ่ายจริงให้ผู้ใช้ดูจาก `/cost` เพราะ session หลักไม่เห็นยอดจริง

## Red flags — ถ้ากำลังคิดแบบนี้ ให้หยุดแล้วทำตามกฎ

| ความคิด | ความจริง |
|---|---|
| "งานนี้ดูสำคัญ ใช้ Opus รีวิวดีกว่า" | ระดับรีวิวมาจาก rubric และ brief เท่านั้น ถ้าคิดว่าเสี่ยงจริง ให้แก้คะแนนความเสี่ยงตั้งแต่ขั้นที่ 3 |
| "เดี๋ยวบอก worker ให้ทำเพิ่มอีกนิด" | brief คือสัญญา สิ่งที่เพิ่มคือ task ใหม่ |
| "worker เถียงมา ตัดสินเองเลยเร็วกว่า" | DISPUTE ต้องให้ reviewer ตัดสิน ผู้จัดการเขียน brief เองจึงไม่เป็นกลาง |
| "QA เปิดหน้าไม่ได้ ก็อ่านโค้ดแทน" | ตอบ `ทดสอบไม่ได้` และแจ้งผู้ใช้ reviewer อ่านโค้ดอยู่แล้ว |
| "FIX อีกรอบเดียวก็น่าจะผ่าน" | ใช้สิทธิ์ FIX ไปแล้ว = ESCALATE |
| "ไม่ต้องใส่ skill หรอก งานง่าย" | ดูตารางในขั้นที่ 4 ก่อนทุกครั้ง |
| "ไม่ต้องส่ง effort / model ก็ได้" | foreman-hud จะปฏิเสธการเรียก และเสียรอบเปล่า |
| "commit ให้ผู้ใช้เลย จะได้เสร็จ" | ผู้ใช้ commit เอง ผู้จัดการแค่ร่างข้อความ commit |
| "สองงานนี้ไม่เกี่ยวกัน ส่งพร้อมกันได้" ทั้งที่แก้ไฟล์เดียวกัน | ไฟล์ซ้อน = ขึ้นต่อกัน ทำทีละตัว |
| "task ผ่านหมดแล้ว ข้ามรีวิวรวมได้" | รีวิวรวมจับปัญหาข้าม task ที่รีวิวราย task มองไม่เห็น |

## จุดที่ต้องหยุดถามผู้ใช้

- ยืนยัน spec (ขั้นที่ 1)
- ก่อนทำสิ่งที่ย้อนกลับไม่ได้: ลบไฟล์, migration, เปลี่ยน schema, push, deploy
- VERDICT เป็น BLOCKED
- ชนเพดานในขั้นที่ 8
- รีวิวรวม (ขั้นที่ 9) ได้ BLOCKED
- จบงาน (ขั้นที่ 10): ให้ผู้ใช้ตรวจและ commit เอง
