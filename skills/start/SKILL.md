# Model Foreman

session หลักคือผู้จัดการ ทำหน้าที่คุยกับผู้ใช้ แตกงาน เลือกโมเดล และตัดสินผล
ควรรัน session หลักด้วย Opus (skill เปลี่ยนโมเดลของ session หลักเองไม่ได้)

หลักการ
- เลือกโมเดลจากความยากของ task ไม่ใช่จากบทบาท Opus เขียนโค้ดเองได้ถ้างานยาก
- คนเขียนกับคนรีวิวต้องไม่ใช่ context เดียวกัน
- spec บอกว่าทำอะไร skill บอกว่าทำแบบไหน worker ต้องใช้ทั้งสองอย่าง

## ขั้นที่ 1 — เคลียร์โจทย์กับผู้ใช้

- ถามกลับในจุดที่กำกวม แย้งเมื่อเห็นว่า requirement ขัดกันเองหรือมีทางที่ดีกว่า
- เขียน spec สั้น ๆ: เป้าหมาย, ขอบเขต, สิ่งที่ไม่ทำ, เกณฑ์ว่าเสร็จ, คำสั่ง test
- **หยุดรอผู้ใช้ยืนยัน spec ก่อนไปขั้นต่อไปเสมอ**

## ขั้นที่ 2 — แตก task

- แยก spec เป็น task ย่อยที่แต่ละอันมีเกณฑ์ผ่านของตัวเอง
- ระบุว่า task ไหนขึ้นต่อกัน task ที่ไม่ขึ้นต่อกันจะส่งพร้อมกันได้
- ให้ id แต่ละ task เช่น T1, T2

## ขั้นที่ 3 — ให้คะแนนและเลือกโมเดล

อ่าน `${CLAUDE_PLUGIN_ROOT}/skills/start/rubric.md` ให้คะแนนทุก task ตามเกณฑ์ แล้วใช้กฎบังคับ
แสดงตารางคะแนนให้ผู้ใช้เห็นตอนเริ่ม (ไม่ต้องรอยืนยัน เว้นแต่มีกฎบังคับให้หยุด)

## ขั้นที่ 4 — ผูก skill กับ task

- ดูรายชื่อ skill ที่มีในเซสชัน แล้วเลือก skill ที่เกี่ยวกับแต่ละ task (เช่น งาน UI → skill ด้าน UI ที่ผู้ใช้มี)
- ใส่ชื่อ skill ลงใน brief ในช่อง "SKILL ที่ต้องโหลดก่อนเริ่ม"
- ห้ามพึ่งให้ worker ค้นเองอย่างเดียว โมเดลเล็กมักมองข้าม skill

## ขั้นที่ 5 — ส่งงานให้ worker

เรียก agent `model-foreman:worker` และระบุ model ตามที่ได้จากขั้นที่ 3
task ที่ไม่ขึ้นต่อกันให้เรียกพร้อมกันในข้อความเดียว

brief ที่ส่งต้องมีครบทุกช่อง เพราะ worker เห็นแค่ brief ไม่เห็นบทสนทนา:

```
TASK: <id> — <ชื่อ>
SPEC ที่เกี่ยวข้อง: <ตัด spec เฉพาะส่วนของ task นี้>
ไฟล์ที่น่าจะแตะ: <path>
SKILL ที่ต้องโหลดก่อนเริ่ม: <ชื่อ skill หรือ "ไม่มี">
เกณฑ์ผ่าน: <ข้อ ๆ>
คำสั่ง test: <คำสั่ง>
ห้ามทำ: <สิ่งที่อยู่นอกขอบเขต>
FEEDBACK รอบก่อน: <ข้อความจาก reviewer หรือ "ไม่มี">
```

ถ้า Claude Code เวอร์ชันที่ใช้ไม่รองรับการส่ง model ตอนเรียก agent
ให้แจ้งผู้ใช้ว่า plugin นี้ต้องการ Claude Code เวอร์ชันที่ส่ง model ให้ agent ได้ แล้วเรียก `model-foreman:worker` ตามปกติ (จะใช้โมเดลเริ่มต้น)

## ขั้นที่ 6 — รีวิว

เรียก agent `model-foreman:reviewer` (Opus, context ใหม่) โดยส่งให้แค่
- brief ของ task
- รายงานจาก worker
- ชื่อ skill ที่ task นี้ต้องใช้

ห้ามส่งความเห็นหรือการตัดสินของ session หลักไปด้วย reviewer จะตอบ VERDICT ข้อใดข้อหนึ่ง: PASS / FIX / ESCALATE / BLOCKED

## ขั้นที่ 7 — แก้และยกระดับ

ลำดับโมเดล: Haiku → Sonnet → Opus

| VERDICT | ความหมาย | ทำอะไรต่อ |
|---|---|---|
| PASS | ผ่านเกณฑ์ | ปิด task |
| FIX | ผิดจุดเล็ก ชี้ได้ชัด | ส่งกลับโมเดลเดิมพร้อม feedback **ได้ 1 ครั้งต่อโมเดล** ถ้าโมเดลนี้ใช้สิทธิ์ FIX ไปแล้ว ให้ถือเป็น ESCALATE |
| ESCALATE | เข้าใจผิด แนวทางผิด หรือคุณภาพไม่พอ | ส่งให้โมเดลถัดไปพร้อม feedback |
| BLOCKED | spec กำกวมหรือขัดกันเอง | หยุด task นี้และถามผู้ใช้ |

เพดาน
- รีวิวได้ไม่เกิน **4 ครั้งต่อ task** ครบแล้วยังไม่ผ่าน → หยุดและรายงานผู้ใช้
- ถ้า Opus ไม่ผ่านหลังใช้สิทธิ์ FIX แล้ว → หยุดและรายงานผู้ใช้ ไม่มีโมเดลให้ยกระดับต่อ
- ถ้ามากกว่าครึ่งของ task ในงานนี้ถูกยกระดับ → หยุดทั้งงานชั่วคราว รายงานผู้ใช้ เพราะมักแปลว่า spec หรือ rubric มีปัญหา

## ขั้นที่ 8 — บันทึกและสรุป

เพิ่มแถวลง `.claude/router-log.md` ของโปรเจกต์ (สร้างพร้อมหัวตารางถ้ายังไม่มี) หนึ่งแถวต่อ task:

```
| วันที่ | task | คะแนน | โมเดลแรก | skill ที่ใช้ | จำนวนรีวิว | โมเดลสุดท้าย | ผล |
```

สรุปให้ผู้ใช้: task ที่เสร็จ, task ที่ค้าง และเหตุผล, โมเดลที่ใช้ต่อ task
ค่าใช้จ่ายจริงให้ผู้ใช้ดูจาก `/cost` เพราะ session หลักไม่เห็นยอดจริง

## จุดที่ต้องหยุดถามผู้ใช้

- ยืนยัน spec (ขั้นที่ 1)
- ก่อนทำสิ่งที่ย้อนกลับไม่ได้: ลบไฟล์, migration, เปลี่ยน schema, push, deploy
- VERDICT เป็น BLOCKED
- ชนเพดานในขั้นที่ 7
