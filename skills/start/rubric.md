# Rubric ประเมินความยาก

ให้คะแนน 0–2 ต่อข้อ ตอบจากสิ่งที่เห็นได้ก่อนลงมือ ไม่ใช่จากความรู้สึกว่ายาก

| เกณฑ์ | 0 | 1 | 2 |
|---|---|---|---|
| ความชัดของ spec | บอกครบว่าทำอะไร ที่ไหน | ต้องตีความบางจุด | ต้องตัดสินใจเองเยอะ |
| ขอบเขต | ไฟล์เดียว | 2–3 ไฟล์ในโมดูลเดียว | ข้ามหลายโมดูล |
| มีแบบให้ดู | มีโค้ดคล้ายกันในโปรเจกต์ | มีบางส่วน | ของใหม่ทั้งหมด |
| ตรวจได้ง่ายไหม | มี test ครอบคลุม | ตรวจด้วยมือได้ | ตรวจยาก ต้องคิดตาม |
| ความเสี่ยง | พังแล้วแก้ง่าย | กระทบส่วนอื่นบ้าง | ข้อมูลเสียหายหรือมีช่องโหว่ |

## แปลงคะแนนเป็นโมเดล

| คะแนนรวม | โมเดล |
|---|---|
| 0–3 | Haiku |
| 4–6 | Sonnet |
| 7–10 | Opus |

## กฎบังคับ (ข้ามคะแนน)

1. แตะ auth, crypto, การจัดการสิทธิ์ หรือการรับ input จากผู้ใช้ → **Opus เสมอ**
2. ย้อนกลับไม่ได้ (migration, ลบข้อมูล, เปลี่ยน schema) → **Opus** และหยุดถามผู้ใช้ก่อนรัน
3. "ความชัดของ spec" ได้ 2 → **ไม่ส่งงาน** กลับไปถามผู้ใช้ก่อน
4. "ตรวจได้ง่ายไหม" ได้ 2 → ปัดขึ้นหนึ่งขั้น เพราะถ้าประเมินพลาด งานผิดอาจผ่านไปโดยไม่มีใครเห็น

## ต้องผ่าน QA ไหม

ใส่ `QA: ต้อง` ใน brief เมื่อ task เข้าข้อใดข้อหนึ่ง
- ผู้ใช้เห็นหรือใช้งานโดยตรง: UI, หน้าเว็บ, ฟอร์ม, API endpoint, คำสั่ง CLI
- แตะความปลอดภัย: auth, การจัดการสิทธิ์, การรับ input จากผู้ใช้, การจัดการไฟล์ที่ผู้ใช้อัปโหลด
- แก้บั๊กที่ผู้ใช้รายงาน (ต้องลองซ้ำว่าหายจริง)

ใส่ `QA: ไม่ต้อง` สำหรับงานภายในที่ test ครอบคลุมพอ เช่น refactor, เขียน docs, แก้ config, เขียน test

QA ใช้ Sonnet เสมอ เพราะงานคือลองใช้แล้วรายงาน ไม่ต้องตัดสินใจเชิงออกแบบ

## เลือกโมเดลของ reviewer

ใช้ข้อแรกที่เข้า แล้วใส่ใน brief ช่อง `ระดับรีวิว`

| เงื่อนไข | reviewer |
|---|---|
| ความเสี่ยงสูง (แตะความปลอดภัยหรือย้อนกลับไม่ได้) | Opus |
| คะแนน 7 ขึ้นไป หรือ worker เป็น Opus | Opus |
| QA รายงานว่า `พบปัญหา` | Opus |
| คะแนน 4–6 | Sonnet |
| คะแนน 0–3 และ worker รายงานว่า test ผ่าน | Haiku (เช็กเร็ว) |
| คะแนน 0–3 แต่ test ไม่ผ่านหรือไม่มี test | Sonnet |

reviewer ทุกระดับตอบ `ESCALATE_REVIEW` ได้เมื่อไม่มั่นใจ แล้วส่งต่อให้ระดับถัดไปรีวิวงานเดิม
ทำให้ใช้ reviewer ราคาถูกได้โดยไม่เสี่ยงว่างานยากจะหลุดผ่าน

## เลือก effort

ส่ง `effort` ทุกครั้งที่เรียก agent และใส่ค่าเดียวกันในบรรทัด `effort:` ของ brief
ห้ามปล่อยให้ agent ใช้ effort ตาม session หลัก เพราะถ้าผู้ใช้ตั้ง session หลักเป็น max ไว้ตอนวางแผน worker ทุกตัวจะได้ max ตามไปด้วย

| บทบาท | เงื่อนไข | effort |
|---|---|---|
| worker | Haiku หรือคะแนน 4–5 | medium |
| worker | คะแนน 6 ขึ้นไป, Opus, หรือความเสี่ยงสูง | high |
| QA | ทั่วไป | medium |
| QA | ความเสี่ยงสูง | high |
| reviewer | Haiku (เช็กเร็ว) | low |
| reviewer | Sonnet | medium |
| reviewer | Opus | high |

ไม่ใช้ `max` กับ agent ตัวไหน เพราะมักได้ผลไม่คุ้มกับ token ที่ใช้คิดเพิ่ม และมีแนวโน้มคิดวนเกินจำเป็น
ถ้า worker ถูกยกระดับ ให้ effort ตามแถวของโมเดลใหม่
